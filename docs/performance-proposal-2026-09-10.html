TL;DR RoseStacker's main-thread cost is dominated by scheduled task volume, not by the work inside those tasks. RoseGarden's Bukkit scheduler wrapper turns every ThreadUtils.runOnEntity() / runOnLocation() call from an async pass into a plain main-thread Bukkit task, so each periodic pass submits one task per entity - roughly 12,000 tasks every 100 ticks for the stacking pass alone, the vast majority of which exit immediately on their first branch. The single highest-leverage change is to move the cheap culls to the async side and drain the survivors from one budgeted main-thread task per tick (finding F1). On the world tick threads the cost is concentrated in the spawner spawn path, where every mob that spawns is fully serialized to NBT even when its storage is discarded microseconds later (B1), and where each unstack cycle materializes a throwaway NMS entity per stack (A2). Phase 1 of the roadmap addresses all three and is low risk.

1. Context

Production is UniverseSpigot 1.21.11, a Paper fork with asynchronous world ticking: each world ticks on its own thread rather than on the primary thread. The server runs 130+ concurrent players with roughly 12,000 living entities, dominated by spawner farms and hopper-fed item farms.

1.1 The architectural fact that shapes everything below

RoseGarden 1.5.7's BukkitSchedulerWrapper - read from the published sources jar - implements both isEntityThread(Entity) and isLocationThread(Location) as Bukkit.isPrimaryThread(), and delegates both runTaskAtEntity(...) and runTaskAtLocation(...) to runTask(runnable), i.e. a plain Bukkit main-thread task. The plugin's own wrapper is a thin pass-through (Plugin/src/main/java/dev/rosewood/rosestacker/utils/ThreadUtils.java:60-73): 

// ThreadUtils.java:68-73 - on a non-Folia server this always takes the second branch
// when called from one of the async stacking passes.
public static void runOnEntity(Entity entity, Runnable runnable) {
    if (SCHEDULER.isEntityThread(entity)) {   // == Bukkit.isPrimaryThread()
        runnable.run();
    } else if (checkEnabled()) {
        SCHEDULER.runTaskAtEntity(entity, runnable); // == Bukkit scheduler runTask()
    }
}

Consequences on this server:

  • Every runOnEntity/runOnLocation from an async pass allocates a Runnable plus a BukkitTask and inserts it into the scheduler's pending-task structure.
  • The world tick threads are not the primary thread either, so calls made from spawner ticking also funnel onto the main thread rather than staying on the world thread.
  • The main-thread heartbeat then drains the whole burst in a single tick. A pass that submits 12,000 tasks produces one very expensive tick every cycle, which is exactly what the 0.90 ms/tick average is smearing out.

Therefore: reducing the number of scheduled tasks per cycle is a bigger lever than optimizing the body of any individual task. Findings A1-A4 and F1 are built around that.

1.2 Things that are not the problem

  • Config lookups. BackedRoseSetting caches the parsed value per reload, so SettingKey.X.get() is a field read. It appears everywhere in these hot paths and is not worth touching.
  • Storage mode choice. Both modes matter: NBT (default) keeps a per-member tag; SIMPLE keeps only a count and clones the head entity on read. Several findings below only apply to one of the two, and each says which.

1.4 In flight (branch perf/spark-2026-09-05, commit d0db5d84)

This proposal assumes the following lands first and does not duplicate it:

  • Removal of the 3-second ChunkSnapshot cache; hasLineOfSight, forEachIntersectingBlock and getLazyBlockMaterial read blocks straight from the loaded chunk.
  • Per-player nametag line-of-sight memo: skip the ray while neither endpoint has moved more than 0.25 block, up to 3 cycles.
  • Condition tags read blocks by coordinate rather than allocating a Location/Block.
  • SpawnerStackSettings pre-partitions per-spawn conditions from spawner-level conditions.
  • MobSpawningMethod's attempt loop reads the spawner coordinates once.

  • EntityCacheManager memoizes the cell across consecutive entities and uses a ConcurrentLinkedQueue; NMSHandlerImpl#getEntities presizes its list.

3. Group A - Scheduled task volume (main thread)

A1. The periodic entity stacking pass schedules one main-thread task per stacked entity

P0 Effort M Risk Low Main thread

Today

stackEntities() runs asynchronously every STACK_FREQUENCY ticks (default 100, Plugin/src/main/java/dev/rosewood/rosestacker/config/SettingKey.java:24) and iterates every StackedEntity in the world (Plugin/src/main/java/dev/rosewood/rosestacker/stack/StackingThread.java:160-186). It performs one cull inline - isRemoved - and then, if ENTITY_REQUIRE_LINE_OF_SIGHT (default true) or ENTITY_DONT_STACK_IF_IN_WATER is enabled, schedules a main-thread task per entity: 

// StackingThread.java:170-183
for (StackedEntity stackedEntity : this.stackedEntities.values()) {
    LivingEntity livingEntity = stackedEntity.getEntity();
    if (this.isRemoved(livingEntity)) { this.removeEntityStack(stackedEntity); continue; }

    if (SettingKey.ENTITY_REQUIRE_LINE_OF_SIGHT.get() || SettingKey.ENTITY_DONT_STACK_IF_IN_WATER.get()) {
        ThreadUtils.runOnEntity(livingEntity, () -> this.tryStackEntity(stackedEntity)); // one main task each
    } else {
        this.tryStackEntity(stackedEntity);
    }
}

On the main thread, tryStackEntity (StackingThread.java:1222-1240) immediately returns for the overwhelming majority: stackSettings == null, checkNPC(), isRemoved(), !hasMoved(), and the WorldGuard test all precede any real work, and hasMoved() is false for AI-disabled farm mobs, which never move.

isRemoved (StackingThread.java:1407-1409) is itself not free: entity.hasMetadata("RS_new") builds a UUID.toString() + ":" + key string and does a synchronized map lookup in CraftBukkit's metadata store, and the Guava REMOVED_ENTITIES.getIfPresent call reads System.nanoTime() on every access.

Why it costs

With ~12,000 living entities, every 5 seconds the main thread receives a burst of ~12,000 task submissions that do nothing. Each costs a Runnable allocation, a BukkitTask allocation, a scheduler insertion under lock on the submitting side, and a drain plus dispatch on the main thread. The main thread pays this all in one tick, so it shows up as a periodic spike rather than as steady load - and spikes are what break the 50 ms budget.

Proposal
  1. Move the culls async. Evaluate stackSettings == null, checkNPC(), isRemoved(), hasMoved() and the WorldGuard test in the async pass, before scheduling anything. Only entities that actually moved get scheduled.
  2. Batch the survivors. Collect them into one list and submit a single main-thread task per cycle that loops them, instead of one task per entity. On Folia, one task per region.
  3. Budget the batch via the executor in F1: drain up to N ms of work per tick and carry the remainder to the next tick, so the burst is spread instead of landing in one tick.
  4. Drop the metadata flag. Replace the "RS_new" Bukkit metadata with a plain boolean field on StackedEntity/StackedItem (or a Set<UUID> owned by the stacking thread), and replace the Guava REMOVED_ENTITIES cache with a ConcurrentHashMap<UUID, Long> pruned in the existing cleanup task.

A2. The unstack pass schedules one main-thread task per stack and materializes a full NMS entity per stack per cycle

P0 Effort M Risk Low-Med Main thread

Today

Every UNSTACK_FREQUENCY ticks (default 50), unstackEntities() (StackingThread.java:188-204) calls tryUnstackEntity (StackingThread.java:205-231) for every stack, and that schedules a main-thread task for each stack with size > 1. On the main thread, for NBT storage, shouldStayStacked (Plugin/src/main/java/dev/rosewood/rosestacker/stack/StackedEntity.java:595-617) builds a complete NMS entity: 

// StackedEntity.java:613-616 - the NBT branch, run per stack per 50 ticks
LivingEntity entity = this.stackedEntityDataStorage.peek()
        .createEntity(this.entity.getLocation(), false, this.entity.getType());
StackedEntity stackedEntity = new StackedEntity(entity,
        nmsHandler.createEntityDataStorage(entity, ...), false);
return this.stackSettings.testCanStackWith(this, stackedEntity, true);

The call chain behind that peek():

  • peek() (NMS/v26_2_R1/src/main/java/dev/rosewood/rosestacker/nms/v26_2_R1/storage/NBTStackedEntityDataStorage.java:98-101) calls rebuild() (…/NBTStackedEntityDataStorage.java:247-252), which allocates a CompoundTag and performs two merges, plus fillAttributeUuids (…:279-292).
  • NBTEntityDataEntry.createEntity (NMS/v26_2_R1/…/storage/NBTEntityDataEntry.java:44-100) copies the tag again at line 48, stores a fresh UUID.randomUUID() at line 59, calls NMSHandlerImpl#createCreature (NMS/v26_2_R1/…/NMSHandlerImpl.java:206-243) which runs Mob#finalizeSpawn - random equipment rolls, attribute rolls, group data - and then runs entity.load(valueInput) over the tag.

This happens for every NBT stack with size > 1, every 2.5 seconds, even when the stack and its head entity have been completely idle. The in-flight branch removes one extra NBT save from the wrapper StackedEntity, but the entity construction itself remains.

Why it costs

This is the 0.14 ms/tick "unstack checks" line, and it is also a second per-cycle task burst on top of A1. The work is pure waste for idle spawner farms: the answer is the same every cycle.

Proposal

Four layers, each useful on its own:

  1. (a) Cull before scheduling, async. Skip stacks whose head entity is not ticking (Paper's Entity#isTicking(), confirmed present on both the 1.21.11 and 26.2 Paper API jars - outside entity activation range, no player nearby): its state cannot have changed. Skip stacks unchanged since the last check, using lastModifiedTicks (already tracked) as the dirty signal, with a conservative fallback that re-checks an idle stack every Nth cycle (e.g. every 4th) so nothing can get permanently stuck.
  2. (b) Batch. One main-thread task per cycle running all due checks, budgeted by F1.
  3. (c) Fast path in NBTStackedEntityDataStorage. The constructor removes every UNSAFE_NBT_KEYS entry from base (…/NBTStackedEntityDataStorage.java:36-44), and addClones() stores straight copies of base, while removeDuplicates() strips keys identical to base. So an entry whose remaining keys are all in UNSAFE_NBT_KEYS (Health, attributes, equipment, brain, ...) differs from the head only in fields the stack conditions do not consult. Add a boolean headIsRepresentative() that tests exactly that, and let shouldStayStacked take the SIMPLE self-compare branch when it is true. PR #8 already made the argument that the self-compare is equivalent; this extends it to the NBT stacks that are effectively clones - which, for spawner-fed farms, is nearly all of them.
  4. (d) When an entity really must be built, make the build cheaper: avoid the second tag copy (rebuild() already returns a fresh tag - add a constructor flag so createEntity does not copy it again), and replace UUID.randomUUID() with Mth.createInsecureUUID(RandomSource) or simply remove the "UUID" key so the entity keeps the UUID it was constructed with. Optionally skip Mob#finalizeSpawn when the tag already carries equipment and attributes; this last sub-item is a behaviour change - clones from SIMPLE storage and addClones() rely on finalizeSpawn to re-roll equipment - and should be decided explicitly rather than folded in.

A3. Nametag and hologram passes still schedule per-stack and per-player main-thread tasks

P1 Effort M Risk Med Both

Today

After PR #12 the nametag pass culls by distance off-thread first, but three scheduling points remain:

  • processNametags (StackingThread.java:314-359) schedules one main-thread task per online player, every 30 ticks, just to snapshot that player's location and main-hand item.
  • processEntityNametags (StackingThread.java:362-439) schedules one task per stack that has any player within 75 blocks (StackerUtils.ASSUMED_ENTITY_VISIBILITY_RANGE, Plugin/src/main/java/dev/rosewood/rosestacker/utils/StackerUtils.java:39), purely so it can call entity.getTrackedBy() on the right thread - and then schedules another task per affected (stack, player) pair to send the packet. processItemNametags (StackingThread.java:441-483) has the same shape.
  • HologramManager#updateWatchers (Plugin/src/main/java/dev/rosewood/rosestacker/manager/HologramManager.java:88-103) schedules one task per online player every HOLOGRAM_UPDATE_FREQUENCY ticks (default 20) - about 135 tasks per second on this server - to read eye locations and reconcile watchers.

Separately, StackedEntity#updateDisplaySafely (StackedEntity.java:744-749) schedules a main-thread task on every stack size change, and the spawner path calls it once per modified stack per spawn cycle (Plugin/src/main/java/dev/rosewood/rosestacker/spawning/MobSpawningMethod.java:345). That is a fourth source of the same problem and should be folded into the same batching.

Why it costs

With 135 players concentrated in farms, hundreds to thousands of tasks per 30-tick cycle. This is currently the largest single consumer inside the 0.90 ms/tick sync-scheduler figure, and the 0.51 + 0.16 ms/tick line-of-sight cost sits inside these tasks on the main thread rather than on an async worker.

Proposal

Make both passes main-thread-free on Paper:

  1. Own the tracker set. The plugin already listens to PlayerTrackEntityEvent and PlayerUntrackEntityEvent (Plugin/src/main/java/dev/rosewood/rosestacker/listener/EntityTrackingListener.java:33-41). Extend it to maintain a Set<UUID> trackedBy on StackedEntity, cleared on PlayerQuitEvent (already handled there at line 43-49). The pass then never needs Entity#getTrackedBy() on the main thread. (getTrackedBy() is declared on both supported Paper API versions, so the current code path is available everywhere; the point of the change is to stop needing the main thread to call it.)
  2. Read player state off-thread. Location doubles are already read racily throughout this file. ItemUtils.isStackingTool(getItemInMainHand()) can either be read racily too or, better, be maintained as a boolean flag updated from PlayerItemHeldEvent and the inventory events. That removes processNametags's per-player snapshot task entirely.
  3. Send packets from the async thread. NMSHandlerImpl#updateEntityNameTagForPlayer (NMS/v26_2_R1/…/NMSHandlerImpl.java:264-278) only builds a ClientboundSetEntityDataPacket and calls connection.send(...), which Netty queues - safe off-thread on Paper. For the stacking-tool particles, build a ClientboundLevelParticlesPacket and send it the same way instead of calling Player#spawnParticle.
  4. Run the hologram watcher update entirely on its async timer. updateWatcher reads the player's eye location, the hologram locations, walks blocks (the in-flight branch reads live chunks) and sends packets. Reading block states off-thread is racy but tolerable for a visibility heuristic; if that is unacceptable, keep only the wall check on-thread and only when the player has moved.
  5. Fall back to the current scheduled path on Spigot (no track/untrack events) and on Folia.
Expected effect

The nametag and hologram passes stop contributing to the main thread at all. Their CPU cost moves to the async pool, where it does not affect MSPT. Given the profile, this is the largest single removal available on the main thread.

Risk

Off-thread reads of entity and player state are racy. The codebase already accepts this for positions, and the failure mode is a nametag that is one cycle stale. Off-thread packet sending is standard on Paper but is the one piece here that has not been confirmed against UniverseSpigot specifically, and is the most likely to surprise; put the whole behaviour behind a config toggle so it can be turned off on a live server without a rollback. Block reads off-thread on a Paper fork with async world ticking need a second look - a chunk being unloaded concurrently must not produce an exception path.

How to verify

The sync scheduler tree should no longer contain StackingThread.lambda$processEntityNametags$… or HologramManager.lambda$updateWatchers$…. Cross-check that the async pool picks up the corresponding time with /spark profiler --thread *.

A4. The orphaned-entity rescan runs on the main thread over every entity in the world

P2 Effort S Risk Low Main thread

Today

cleanupOrphanedEntities (StackingThread.java:242-256) is registered with the synchronous timer (StackingThread.java:119-120) and runs every ENTITY_RESCAN_FREQUENCY ticks (default 1000). It calls this.targetWorld.getEntities(), which allocates a list of every entity in the world, then per entity calls isRemoved (the metadata string build from A1) and, for unstacked candidates, stackManager.isAreaDisabled(entity.getLocation()) - a WorldGuard region query when WorldGuard is installed.

Why it costs

One 12,000-element list allocation plus 12,000 metadata lookups and up to 12,000 region queries, all inside a single tick, every 50 seconds. It is a small average but a visible spike.

Proposal

Run the scan asynchronously over the EntityCacheManager cells (or nmsHandler.getEntities(world)), and schedule only the rare createEntityStack calls - through the F1 batch executor. Combine with the isRemoved flag change from A1 and the per-chunk WorldGuard cache from D3, both of which this scan benefits from directly.

Expected effect

The 1000-tick spike flattens to whatever number of genuinely orphaned entities exists, usually zero.

Risk

Iterating the world entity list off-thread is not safe in general; use the cache manager's snapshot cells rather than World#getEntities, and accept that an entity that spawned in the last 60 ticks may be picked up on the next pass instead.

How to verify

StackingThread#cleanupOrphanedEntities should vanish from the main-thread tree. Log the number of stacks created per rescan; if it is not near zero, the rescan is masking a bug worth fixing separately.

4. Group B - Spawner tick and spawn path (world tick threads)

B1. Every entity stack creation eagerly serializes the entity to NBT, including the stacks that stay at size 1

P0 Effort M Risk Low Tick thread

Today

The NBT storage constructor performs a full entity save up front: 

// NMS/v26_2_R1/…/storage/NBTStackedEntityDataStorage.java:36-44
public NBTStackedEntityDataStorage(LivingEntity livingEntity) {
    super(StackedEntityDataStorageType.NBT, livingEntity);
    this.base = ((NMSHandlerImpl) NMSAdapter.getHandler()).saveEntityToTag(livingEntity); // Entity#saveWithoutId
    this.stripUnneeded(this.base);
    this.stripAttributeUuids(this.base);
    NMSHandler.UNSAFE_NBT_KEYS.forEach(this.base::remove);
    this.data = createBackingQueue();
}

StackedEntity's convenience constructor creates that storage unconditionally (StackedEntity.java:117-119), and it is called from every path that produces a stack:

  • createEntityStack on every CreatureSpawnEvent and on chunk load (StackingThread.java:774-791)
  • StackingThread#createNewEntity, the helper behind preStackEntities (StackingThread.java:943-949)
  • one per spawned mob in the spawner path (MobSpawningMethod.java:308 and :336)
  • the split-off entity in decreaseStackSize (StackedEntity.java:225)

In the NBT spawner path the save happens twice per mob: new StackedEntity(...) saves the entity into its own base, and then increaseStackSize(newStack.getEntity(), false) calls add(LivingEntity) (…/NBTStackedEntityDataStorage.java:72-80) which saves the same entity again. The first storage is then discarded.

Why it costs

Entity#saveWithoutId walks every component of the entity through a TagValueOutput with a ProblemReporter and allocates a tag tree per call. Running it for every mob that spawns, loads, or is split off - on the world tick thread, inside spawner ticking - is the dominant per-spawn cost after entity construction itself, and it is entirely wasted for the ~99% of stacks that never grow past size 1 or that merge immediately.

Proposal
  1. Make base lazy. Compute it on first use - that is, in add, addAll, addClones, peek/pop/getAll, serialize, removeDuplicates and rebuild. Note that serialize is only ever reached for size > 1, because DataUtils#writeStackedEntity returns immediately for size 1 (Plugin/src/main/java/dev/rosewood/rosestacker/utils/DataUtils.java:96-98).
  2. Reuse the tag in the spawner path. Add an add(EntityDataEntry) / add(CompoundTag) overload on the storage and hand the already-saved tag to it when the spawned mob merges into an existing stack, instead of saving twice. The NBTEntityDataEntry(LivingEntity) constructor (NMS/v26_2_R1/…/storage/NBTEntityDataEntry.java:32-34) already produces exactly that tag.

B2. The spawner spawn-attempt loop repeats work per attempt and per spawn

This runs on an async worker so it does not directly add MSPT, but on a server with thousands of ground items it is significant CPU and allocation pressure competing with the world tick threads for cores and for GC. ItemStack#isSimilar in particular is expensive on items with meta.

Proposal
  1. Apply the same hasMoved/isRemoved pre-cull as A1 and the flag caching from D2.
  2. Group nearby items by a cheap key first - Material plus an item-meta hash (Paper's ItemStack#hashCode is suitable) - so that isSimilar only runs on candidates whose key already matches.
  3. Drop the intermediate stream and set; iterate the cache manager's result directly into the existing target collection.
Expected effect

Fewer full item comparisons and much less garbage per cycle; frees CPU for the tick threads.

Risk

The grouping key must be a strict refinement of isSimilar, or items that should merge will stop merging. If in doubt, use the key only as a fast-reject filter and always confirm with isSimilar.

How to verify

StackingThread#tryStackItem in a --thread * profile, and ItemStack#isSimilar sample count per cycle.

7. Group E - Persistence and spikes

E1. Autosave and chunk unload serialize every stack, every time

P2 Effort S Risk Low Main thread

Today

StackingThread#saveAllData (StackingThread.java:1197-1214) is driven by the autosave timer every AUTOSAVE_FREQUENCY minutes (default 15, Plugin/…/config/SettingKey.java:29, Plugin/src/main/java/dev/rosewood/rosestacker/manager/StackManager.java:83) and walks every stacked entity, every stacked item and every chunk's blocks and spawners in a single tick. For each stack with size > 1, DataUtils#writeStackedEntity (Plugin/…/utils/DataUtils.java:96-126) serializes and GZIPs the whole storage and writes it into the entity's PDC.

The chunk-unload path (saveChunkEntities / saveChunkEntityStacks, StackingThread.java:1148-1195) does the same per unload, and builds several intermediate streams and lists on the way.

Why it costs

A single tick every 15 minutes that GZIPs thousands of NBT payloads. It does not move the average much, but it is one of the largest single-tick stalls the plugin produces, and unload-time serialization is on the critical path of chunk unloading.

Proposal
  1. Dirty tracking. Store a lastSavedModifiedTicks alongside the existing lastModifiedTicks and skip any stack whose value has not changed since the last save. On a settled server most stacks are unchanged between autosaves.
  2. Spread the work. Save N stacks per tick through the F1 budgeted executor rather than all of them in one tick.
  3. Move the expensive half off-thread. Serialization and GZIP need no main-thread state once the storage snapshot is taken; only the PDC write must happen on the entity's thread.
  4. Replace the stream chains in saveChunkEntities with direct loops.
Expected effect

The 15-minute stall becomes proportional to the number of stacks actually modified, spread across ticks.

Risk

Dirty tracking must be conservative: any mutation that does not bump lastModifiedTicks would silently stop being saved. Audit every writer of the storage before relying on it, and keep a "save everything" path for shutdown and for /rs reload.

How to verify

Watch for the periodic spike in spark's tick monitor at the autosave interval; log stacks saved versus stacks skipped per autosave.

Why it costs

Rebuilding a 12,000-entry multimap every 60 ticks, plus a string hash per entity, plus a window during which readers can observe a partially rebuilt cache while holding the same lock.

Proposal
  • Build the replacement map into a fresh structure and swap the reference atomically. Readers never see a half-built cache, and the clear() plus rehash cost disappears.

  • Size the cell collections as ArrayList; readers only iterate them.

Expected effect

Roughly halves the refresh cost and removes a lock-contention window against the async stacking passes.

Risk

Reference swapping changes the visibility semantics slightly: a reader that captured the old map keeps reading 60-tick-old data for the duration of its pass, which is the same staleness bound as today.

How to verify

EntityCacheManager#refresh in the main-thread tree; compare ms/tick against the 0.17 baseline.

8. Group F - Cross-cutting mechanism

F1. A batched, budgeted main-thread executor

P0 (enabler) Effort M Risk Low Main thread

Today

Each periodic pass calls ThreadUtils.runOnEntity per item, which on a non-Folia server means one Bukkit main-thread task per item - this is what RoseGarden 1.5.7's BukkitSchedulerWrapper does, confirmed against its published sources (see section 1.1). The main thread drains the whole burst in the tick after it is submitted, so the plugin's worst-case per-tick cost is unbounded and grows with entity count.

Why it costs

MSPT is decided by the worst ticks, not the average. A design that submits O(entities) tasks in a burst has no ceiling. A design that drains a queue under a time budget has one, by construction.

Proposal

Add a small utility - one repeating main-thread task per world (or per region on Folia) that drains a queue under a configurable per-tick budget, with a max-age guarantee so nothing starves: 

public final class BatchedMainThreadExecutor {

    private final Queue<Job> queue = new ConcurrentLinkedQueue<>();
    private final long budgetNanos;   // e.g. 2 ms
    private final long maxAgeTicks;   // hard deadline; over-run the budget rather than starve

    /** Called from the async passes. Never blocks, never allocates a BukkitTask. */
    public void submit(Runnable job) { this.queue.add(new Job(job, currentTick())); }

    /** The one repeating main-thread task. */
    private void drain() {
        long deadline = System.nanoTime() + this.budgetNanos;
        Job job;
        while ((job = this.queue.poll()) != null) {
            job.run();
            if (System.nanoTime() >= deadline && !this.queue.isEmpty()
                    && currentTick() - this.queue.peek().submittedTick() < this.maxAgeTicks)
                break;  // carry the rest to the next tick
        }
    }
}

Usage rules:

  • Periodic passes (A1, A2, A3 fallback, A4, E1) submit batches - one job that loops a list - rather than one job per entity, so the queue stays short and the per-job overhead is amortized.
  • Event-driven, latency-sensitive work keeps using ThreadUtils.runOnEntity directly. This executor is for periodic maintenance only.
  • On Folia, back it with per-region repeating tasks and route each job to the region owning its location; the budget logic is unchanged.
  • Expose the budget as a config value (default 1-2 ms) plus a debug counter of queue depth, so the behaviour is observable on a live server.
Expected effect

Converts "thousands of tasks per cycle, drained in one tick" into "one task per tick that never exceeds its budget". This directly caps RoseStacker's main-thread MSPT contribution rather than merely reducing it, which matters more than the absolute number: the plugin stops being able to cause a spike proportional to entity count.

Risk

Work can be delayed by a tick or more under load. Every caller must tolerate that, which is why only the periodic passes should use it. The max-age guarantee prevents indefinite starvation if the queue grows faster than the budget drains it; if that condition is hit regularly it is a signal that the upstream pass frequency is too high, and should be logged rather than silently absorbed.

How to verify

Exactly one repeating node per world in the sync scheduler tree, with a bounded self-time. Log queue depth and per-tick drain time at a debug level; the queue should return to empty within a cycle under normal load.
