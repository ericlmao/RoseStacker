TL;DR Every finding in the proposal (A1-A4, B1-B4, C1-C5, D1-D5, E1-E2, F1) is implemented on perf/proposal-impl-2026-09-10 and open as PR #14. The central change is F1: a single budgeted main-thread task (BatchedMainThreadExecutor) now drains all periodic work under misc-settings.main-thread-task-budget-ms (default 2.0), and the cheap culls that used to run inside those tasks run off-thread before anything is scheduled. With misc-settings.async-display-updates (default true) the nametag and hologram passes leave the main thread entirely on Paper. On the world tick threads, the spawner path no longer serializes every mob to NBT twice (B1), no longer runs an 800-probe random search on a saturated farm (B2), and no longer walks the player list per spawner (B3). An independent review of the merged diff found one blocker and ten smaller items; all eleven are fixed in the final eight commits.

To validate: deploy the jar, let the server settle for 15 minutes, take a spark profile at a comparable player count, and compare the nodes listed in section 6. Both new settings can be turned off at runtime with /rs reload to A/B the change without a restart.
What is measured and what is modelled The baseline numbers in this report are measured (spark, 2026-09-05, 135 players, ~16 TPS). Everything in section 4 is a model: an arithmetic projection from the code that shipped, not a measurement of it. No post-change profile exists yet. Every chart states its assumptions and shows the arithmetic beside it so the numbers can be re-derived or disputed.

1.1 Deviations from the proposal

IDDeviation
A2The head-entity fast path is bounded, which the proposal did not call for. A full materialized comparison is forced every 8 unstack passes, and an Ageable head whose adult state disagrees with the stored base takes the full comparison immediately. See section 3.
A3Not unconditional. The async path is behind misc-settings.async-display-updates and falls back to the scheduled path on Folia, on Spigot, when the tracking events are unavailable, or when the setting is off. Wall checks now read block data off the main thread, which is a documented behaviour change rather than a pure move.
A4The rescan itself stays on the main thread. Iterating the level's entity list off-thread is not safe, so only the stack creations it finds were moved onto the executor. The win is the removal of the full entity-list copy, not the removal of the scan.
B1The proposal's second half - "reuse the tag on merge so the spawner path saves once instead of twice" - turned out to need no code. Once the base is lazy, the throwaway per-mob storage never captures a base at all, so the second save disappears as a consequence of the first change. No merge-time tag reuse was added.
B2finalizeSpawn behaviour is intentionally unchanged. The proposal floated skipping or deferring it for mobs that merge straight into a stack; that would change equipment and variant rolls that players can observe, so it was left alone. The win comes from the offset cache and the allocation removals only.
B4Partial. The condition's own scan is now a counting walk with an early exit, but it is still a second walk: the spawn path's later nearby scan is not shared with it. Sharing the two would require threading a result through the condition-tag interface, which was judged out of proportion to the remaining cost.
C1Version-split. The UUID key is dropped from stored tags only on 1.21+, where javap over the compiled-against Spigot jars confirms Entity#load only overwrites the UUID when the key is present. The six modules for 1.20.6 and earlier still write a UUID; they only swap the source from SecureRandom to ExtraUtils.insecureRandomUuid(). C3Hardened during review into a copy-on-write: damageAll builds a new tag per survivor rather than mutating the published ones, because readers snapshot tag references under the lock and then read them outside it. It also calls markStorageModified so a health-only change is visible to the autosave dirty check.

2. Mechanisms, by group

2.1 Group A - Scheduled task volume (main thread)

RoseGarden's BukkitSchedulerWrapper implements isEntityThread(Entity) and isLocationThread(Location) as Bukkit.isPrimaryThread() and delegates runTaskAtEntity / runTaskAtLocation to a plain runTask. On a non-Folia server, every ThreadUtils.runOnEntity() call from one of the async passes is therefore a Bukkit main-thread task. The stacking pass made one per stacked entity every 100 ticks, the unstack pass one per stack every 50 ticks, the nametag pass one per stack per cycle, and the hologram pass one per player per cycle. The main thread drains that entire burst in the tick after it is submitted, so the plugin's worst-case per-tick cost had no ceiling and grew with entity count. MSPT is decided by the worst ticks, so the burst matters more than the mean.

The fix has two halves. First, every cull that already gated the real work now runs on the async pass thread before anything is scheduled: null settings, the NPC check, the removal check, hasMoved() and the WorldGuard test. On a farm-heavy world nearly every stack fails hasMoved(), because AI-disabled mobs do not move, which means the burst of tasks was almost entirely no-ops. hasMoved() records the position it reads, so it deliberately runs exactly once per stack per cycle and is not repeated on the main thread. Second, the survivors are submitted to BatchedMainThreadExecutor in batches of 64.

The unstack pass adds two more culls: head entities that Paper reports are not ticking cannot have changed since the last pass, and stacks whose modified tick has not moved reach the verdict they reached last time. Idle stacks are still re-checked every fourth cycle. On top of that, shouldStayStacked takes a cheap self-compare path when the storage reports its head entry is representative - see 2.3.

Two allocations were removed from paths that run tens of thousands of times per cycle. The RS_new Bukkit metadata flag, whose hasMetadata built a UUID string and took a synchronized lookup on every removal check, is a plain field on the stack objects. The Guava removed-entity cache, which read System.nanoTime() on every access, is a plain map of removal timestamps pruned by the passes that already run, with the same five second semantics.

Display updates are the other half. On Paper, EntityTrackingListener maintains the set of players tracking each stack, so the nametag pass never has to call Entity#getTrackedBy() on the entity's thread; the stacking tool flag is maintained from the events that can change it instead of being read in a task per player per cycle; and both the nametag metadata packet and the stacking tool particles are sent from the async pass. StackedEntity#updateDisplay sends to the tracked set directly. HologramManager's watcher update runs on its own async timer. All of it sits behind misc-settings.async-display-updates.

2.2 Group B - Spawner tick and spawn path (world tick threads)

B1, the lazy base. NBTStackedEntityDataStorage called Entity#saveWithoutId in its LivingEntity constructor, so every mob that spawned, loaded from a chunk or split off a stack walked its whole component tree through a TagValueOutput and allocated a tag tree for it. The base is only ever used as a template for new entries and as the deduplication baseline, and roughly 99% of stacks never grow past size 1, so that save was thrown away almost every time. The spawner path was worse: it saved each spawned mob once into its own throwaway storage and then a second time into the stack it immediately merged into. The field is now captured on first use by getBase(). Capturing later is at least as accurate as capturing earlier: it is still the head entity's own data. The deserializing constructor keeps its eager base, since the stored bytes are the only copy of it that exists.

B2, the attempt loop. A saturated farm ran the whole random search every spawn cycle - up to max-failed-spawn-attempts times spawn-range squared, 800 block probes with the defaults - and each attempt allocated a Location for the invalid-position multimap (hashing three doubles) plus an array list per failed position. Farms are static, so the offsets that produced a valid spawn are remembered on the StackedSpawner and re-checked before any random sampling. Offsets that no longer pass are dropped, ones the search finds take their place, and ones the search stopped short of are carried over; a stale entry costs a single wasted block probe. Sixteen offsets covers the most locations a cycle asks for. Separately, each spawn allocated a MobSpawningMethod and with it a Random whose constructor runs a seed-uniquifier CAS loop, and re-parsed the entity type from a NamespacedKey; the tile now keeps one spawning method per entity type and draws from ThreadLocalRandom. Spawning into nearby stacks tries the last match first and falls back to the scan.

B3, player activation. Spawner activation went through the level's own nearby-player check, which walks every player in the level, run per loaded stacked spawner every player-check-frequency ticks: a cost that grows as spawners times players, paid on the world tick thread before any spawning work happens. Each world now keeps one NearbyPlayerSnapshot of activating player positions, refreshed at most once per tick and only when something asks, and the check is primitive math. A snapshot can be one tick stale, which cannot change the outcome of a check that already only runs every tenth tick against a radius measured in whole blocks. It is also version independent, unlike the server's own spatial structures.

B4, the nearby-entity count. MaxNearbyEntityConditionTag ran a full getNearbyEntities scan per spawner per spawn cycle and threw the result away after comparing its size against a threshold. EntityCacheManager#countNearbyEntities walks the same cells without collecting anything and stops as soon as the limit is reached, with an optional weigher so the include-stacks path can sum stack sizes and keep the early exit.

2.3 Group C - Entity data storage and the NMS layer

The representative-head shortcut (A2/C-adjacent). shouldStayStacked built a complete NMS entity out of the front storage entry for every stack of size > 1, every unstack cycle, purely to compare it against the stack it came from: a tag merge plus createCreature plus finalizeSpawn plus entity.load, for thousands of idle spawner-fed stacks every 2.5 seconds. Entries are stored deduplicated against the base, and the base already has every UNSAFE_NBT_KEYS entry stripped. An entry whose remaining keys are all unsafe keys therefore differs from the head entity only in fields the stack conditions never consult - health, equipment, attributes, brain - so the head entity is an equally valid stand-in. StackedEntityDataStorage#isHeadRepresentative() reports exactly that; the simple storages report true unconditionally, since each of their entries is already a stripped copy of the head. The unsafe key list gained a set view so the test does not linear-scan sixty strings per key per stack per cycle.

Tag copies and UUIDs. rebuild() already allocates a fresh CompoundTag and merges the base and the member tag into it, and every caller wrapped that private, freshly built tag in an NBTEntityDataEntry - which then copied the whole tag again. Entries now carry an owned flag: entries built from a rebuild() result edit in place, while entries built from a LivingEntity or an externally supplied tag still copy, because those tags are handed back out through get(). createEntity also stored a fresh UUID.randomUUID() into the tag on every call; on 1.21+ that is unnecessary and removing the key instead keeps the entity's own UUID for free, taking a synchronized SecureRandom draw off the unstack and kill paths.

Shared damage. When a damage cause is listed in share-damage-conditions, EntityListener#onEntityDamage fed a health-subtracting function to removeIf. For NBT storage that built a complete NMS entity out of every member to read and write one float, then saved every survivor back out: a 500-mob stack standing in lava produced 500 createCreature calls and 500 saveWithoutId calls per damage tick, on the main thread, inside an event handler. damageAll(double) now edits the Health float and materializes only the members that died, since the loot code needs real entities for those. Members added by addClones() inherit from a base with health stripped, so their health comes from one entity built out of the base, once per stack.

Backing collection. The queue was a LinkedBlockingQueue, so every add, remove and iteration took the queue's internal lock and allocated a node per entry, while the bulk operations already wrapped themselves in synchronized (this.data). It is an ArrayDeque under that one lock now; snapshots are taken inside the lock and tag merging and entity construction happen outside it. size() and isEmpty() read a volatile int mirror written only under the lock, so they stay a plain field read on a path that runs constantly.

2.4 Group D - Caching layers

PersistentDataUtils allocated a NamespacedKey on every flag read, and the constructor lowercases and validates both halves before PersistentDataContainer#has rebuilds the namespace:key string again. The stacking conditions run those reads for every candidate pair of every stacking pass, which made this the highest-multiplicity allocation in the plugin. Keys are built once, lazily; the flags themselves are cached on StackedEntity and StackedItem, cleared through the setters and on head-entity replacement. StackConditions only reads a cached flag when the entity it is testing is that stack's own head.

Display strings had the same shape of waste: updateDisplay() clears the memo on every call, and every spawner spawn that merges into a stack triggers one, so each rebuild ran a placeholder replacement plus four colorify regex passes to produce a string thousands of other stacks already have. There is now a bounded cache keyed on everything the message depends on, invalidated when the locale generation counter changes.

The WorldGuard hook ran a fresh RegionQuery for every listener call and every stack candidate, even though the rosestacker flag defaults to true and can only ever deny a location inside a region that explicitly sets it. The hook now caches per chunk whether any overlapping region defines the flag (counting parent regions and the global region) and answers the common "nothing here cares" case from a map. There is no cross-version region change event, so entries expire 30 seconds after they are computed and the cache is cleared on reload; a region edit is honoured within that window.

Two per-spawner items: getHologramLocation allocated a Location through Block#getLocation on every call, twice per hologram cycle per loaded spawner, and updateSpawnerProperties called up to six tile setters each of which broadcast a block update, so one stack size change produced six broadcasts. The Location is cached and rebuilt only when the configured height offset changes; the tile can have updates suppressed for a batch and sends a single update at the end. The CreatureSpawner snapshot, documented as very stale already, is only re-taken when the spawner's type changes.

2.5 Group E - Persistence and spikes

The autosave walks every stacked entity and item in the world in a single tick and, for each stack larger than one, serializes and GZIPs its whole storage into the entity's persistent data container. On a settled server most stacks have not changed at all since the last autosave 15 minutes ago, so nearly all of that produces byte-for-byte the payload that is already stored. It does not move the average much, but it is one of the largest single-tick stalls the plugin produces. StackedEntity now records what it looked like when it was last written and the autosave skips stacks that still look that way. The check is deliberately conservative: it compares stack size as well as modified tick, so a storage mutation that went around markModified still counts as a change. Whatever is left goes to the executor in groups.

The entity cache refresh cleared the live cell map and refilled it in place every 60 ticks, so every reader in that window saw a partially rebuilt cache while holding the same lock, and the clear plus rehash was paid on the tick thread. It now builds the replacement off to the side and swaps the reference in when complete; readers grab the reference once and iterate a consistent snapshot no more stale than before. Cells used to be keyed by a record holding the world name, hashing a String per insert and per lookup; worlds now get a dense index and the key packs that index with the cell coordinates into a single long.

2.6 Group F - The batched main-thread executor

BatchedMainThreadExecutor is one repeating main-thread task that drains a queue under misc-settings.main-thread-task-budget-ms (default 2.0), carrying whatever does not fit to the next tick. Three properties matter:

  • No starvation. A job that has waited MAX_JOB_AGE_TICKS (40) runs regardless of the budget, so a permanently saturated queue still makes progress on its oldest work.
  • Per-job isolation. An exception in one job no longer stops the drain, and after fc9a84d1 each per-stack action inside a batch runs in its own guard, so one failing stack cannot take the other 63 in its batch with it. That mattered specifically for the unstack pass, where the job is what releases a stack's claim in pendingEntityUnstackChecks: a skipped job meant that stack was never checked again while its entity lived.
  • Folia. There is no single main thread to drain from, so jobs are still routed to the region that owns their entity or location. The budget setting has no effect there.

stop() counts and logs any jobs it discards when called off the main thread. That branch is latent today - StackManager#disable stops the executor from the main thread - but a silent queue drop is expensive enough (held unstack claims) that it should not go by quietly if that ever changes.

3. Review and hardening

The merged diff was reviewed independently after the feature work was complete. The review found one blocker and ten smaller items. All eleven are fixed in the final eight commits (65dd7b51 through fc9a84d1). None of them were found by testing; they were found by reading. That is worth stating plainly, because it means the same class of defect may still be present in the parts of the diff the review did not reach, in particular the six hand-edited legacy NMS modules.

3.1 The blocker

The isHeadRepresentative fast path compares a stack against its own head entity whenever the front stored entry differs from the frozen base tag only in unsafe keys. That equivalence holds only while the head entity still matches the base - and the head keeps being simulated after the base was captured. A baby grows up. A sheep regrows its wool. A player tames an animal. The stack then compares equal to itself forever and never splits, where master materialized an entry every cycle and split within one unstack pass. For a spawner farm full of baby mobs that is a visible, permanent behaviour regression, not a performance nuance.

The fix (65dd7b51) keeps the shortcut but bounds its staleness two ways:

  • A cycle bound. StackedEntity counts the unstack passes it has answered from the head and forces the full materialized comparison every FULL_UNSTACK_CHECK_CYCLES (8) passes. The counter is incremented in needsUnstackCheck, including on passes the idle skip drops, so the every-fourth-cycle idle recheck cannot stretch the deadline past 8 passes. At the default 50 tick unstack frequency that is 20 seconds worst case before a diverged head splits, against 2.5 seconds on master.
  • An age guard. Aging is the one divergence that happens with nothing touching the stack at all, so it gets an immediate check: storages expose the adult state their entries are stored against through StackedEntityDataStorage#getBaseAdultState(), the NBT implementations read it out of the lazily captured base tag, and a head Ageable whose adult state disagrees takes the full comparison right away.

The residual is a real, accepted regression: a stack whose head diverges in some way other than age can stay merged for up to 20 seconds where master would have split it in 2.5. That is the price of the shortcut and it is the number to watch if players report mismatched stacks.

The two spawn-reason flags are only remembered once the entity is in the world; container-only flags are unaffected, since their setters clear the cache.

5. Behaviour changes to be aware of

Everything here is a deliberate, documented change in observable behaviour. None of it is a bug, but all of it is something a server operator or a downstream plugin could notice.

  1. Unstack split latency is bounded, not immediate. A stack whose head entity diverges from its stored members in a way the age guard does not catch can stay merged for up to 8 unstack passes, which at the default 50 tick frequency is 20 seconds. Master split within one pass, 2.5 seconds. The Ageable case (a baby growing up) is checked every pass and is not subject to the bound.
  2. SpawnerSpawnEvent#getSpawner returns a less frequently refreshed snapshot. The CreatureSpawner block state is now re-taken only when the spawner's entity type changes, not on every stack size change. The snapshot was already documented as very stale, but a plugin reading getSpawner().getSpawnCount() or similar out of the event may now see an older value than before.
  3. Shared damage no longer re-rolls equipment. The old path rebuilt every survivor from a freshly materialized entity, which baked finalizeSpawn's random equipment rolls into entries that previously carried none. Editing the stored Health float in place stops that. Stacks that take shared damage will no longer spontaneously acquire equipment, which is a fix, but it does change what those stacks drop.
  4. Nametag and hologram packets are sent from non-main threads when misc-settings.async-display-updates is true (the default, Paper only, never on Folia or Spigot). A plugin that intercepts outbound entity metadata packets and assumes the main thread will see them on a different thread.
  5. Line-of-sight wall checks read block data off the main thread under the same setting, and may see a block a moment out of date. A read that throws because the server is resizing a section palette is treated as air, that is, as passable, for that cycle. The setting's config comment says so.
  6. WorldGuard region edits take up to 30 seconds to be honoured in the chunk-level flag cache. /rs reload clears it immediately. Chunks that do contain a region defining the rosestacker flag still fall through to the exact per-location query, so only the "this chunk has no flagged region" answer is cached.
  7. Spawner activation can be one tick stale. NearbyPlayerSnapshot refreshes at most once per tick. The check it feeds already only runs every player-check-frequency ticks against a radius in whole blocks.
  8. Entity cache: a world that loaded since the last refresh is treated as having nothing cached until the next refresh, at most three seconds later. That is the same answer the old code gave a world on its first cycle. Past 4,096 simultaneously loaded worlds the excess is left uncached and a warning is logged once.
  9. Autosave writes are delayed, never skipped. Only the periodic autosave skips unchanged stacks and spreads its writes across ticks. Chunk unload, world transfer, reload and shutdown still write everything unconditionally.
  10. Spawner failure reports are computed from random attempts only. Cached-offset re-checks are not counted as attempts and no longer contribute to the condition tally, so the reported blame condition matches master's.
  11. Fallbacks and toggles. misc-settings.main-thread-task-budget-ms (default 2.0) controls the drain budget and has no effect on Folia. misc-settings.async-display-updates (default true) falls back to the old scheduled path when off, on Folia, on Spigot, or when the entity tracking events are unavailable. Both are re-read on /rs reload, so either can be turned off on a live server without a restart.
